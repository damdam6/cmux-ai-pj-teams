# 태스크 코드 아키텍처 문서

기본 경로: `raw/tasks/{project}/design/{slug}/code-archi.md`. 저장소가 지정한 태스크 설계
문서가 있으면 그 경로를 사용한다. 프로젝트 archi, code-archi, 구현 plan은 별도 md로 유지한다.
pj-plan의 같은 planner가 code-archi와 plan을 모두 완성한 뒤 worker에게 인계한다.

```markdown
# {태스크 이름} 코드 아키텍처

## 기준과 범위
- 프로젝트 archi: 경로와 적용할 절/계약.
- 태스크 정의 및 구현 계획: {slug}.md 링크.
- 이번 설계가 담당할 범위.

## 기존 코드와 재사용
조사한 파일·심볼, 기존 패턴·의존성·테스트 경계, 활용할 구현.
관찰한 사실과 제안을 구분한다.

## 컴포넌트와 인터페이스
| Repo / 파일·심볼 | 현재/신규 | 책임 | 인터페이스·의존성 |
|---|---|---|---|

## 호출·데이터 흐름
입력부터 결과까지의 흐름, 상태 소유자, 해당되는 검증·오류·동시성·통합 경계.

## 설계 결정
선택한 방법과 이유, 검토한 대안, 프로젝트 archi에서 달라진 계약이 있다면 그 내용.
일반 실행의 사용자 결정인지 pj-night의 자율 결정인지 표시한다.
```

작은 변경은 필요한 내용을 몇 줄로 작성하면 충분하다. 적용되지 않는 하위 내용은 생략한다.
프로젝트 설계를 복사하거나 새 프레임워크·추상화를 당연한 전제로 넣지 않는다. 코드 경로는
repo 상대 경로로 쓰고 여러 repo면 어느 repo인지 명시한다.

구현 순서·완료 조건·검증 명령·Simplifier 선택·작업 인계는 `{slug}.md`의 책임이다. 설계 결정을
바꾸면 code-archi를 갱신하고 영향을 받는 plan의 단계/검증/인계도 함께 맞춘다.

별도 문서라는 이유로 worker에게 설계를 미루지 않는다. 두 문서 모두 저장돼 있고, plan의
`설계 참조`와 `작업 인계 > 참조 문서`에서 이 문서를 찾아 읽을 수 있어야 인계 준비가 끝난다.
이벤트의 기본 경로는 `raw/tasks/{project}/design/{slug}/code-archi.md`로 쓰고 이유에
`vault-relative`를 명시한다. worker는 plan과 같은 vault 루트에서 이를 읽는다. 기존 transport는
절대 경로와 `..`를 거부하므로 사람이 누를 plan 링크와 이벤트 경로 표기를 구분한다.
