# 계획 문서 스키마

`raw/tasks/{project}/{slug}.md` 한 파일. pj-task-regi 가 적재 때 프론트매터와 `## 최초 요청` 까지
만들어 두고, pj-plan 이 나머지를 채운다. pj-work 는 **별도 세션에서** 이 문서를 스펙으로 읽는다 —
계획 세션의 대화 맥락은 워커에게 전달되지 않으므로, 이 문서와 연결된 code-archi를 읽는다.

코드 설계는 별도 문서 `raw/tasks/{project}/design/{slug}/code-archi.md`에 쓴다. 저장소가 정한
태스크 설계 경로가 있으면 그 경로를 사용한다. 스키마는 `code-archi-schema.md`에 있다.
이 계획에는 그 문서의 링크와 구현 순서를 담고, 파일별 설계·데이터 흐름 본문을 복사하지 않는다.

같은 폴더의 `project.md` 는 프로젝트 전체의 목표·범위·`ctx`·`docs` 를 갖는다. 여러 작업에 걸치는
맥락은 거기 있고 여기 복사하지 않는다 — `repo` 도 프로젝트의 것이라 이 문서에 없다.

## 뼈대

```markdown
---
project: ds-migration
slug: item-search-hide
branch: fix/item-search-hide      # pj-plan 이 추가
created: 2026-08-03
---

# Item 검색창 노출 제거

## 최초 요청
(pj-task-regi 가 적재 때 넣은 사용자 발화 — 절대 고치지 않는다)

## 태스크 정의
(pj-task-plan에서 전달된 범위·대상 repo·완료 조건·archi 참조가 있으면 보존한다)

## 현황
지금 코드가 어떻게 돼 있는지. 파일·심볼 단위로 구체적으로.

## 목표
끝났을 때 무엇이 참이어야 하는지. "안 하는 것"도 여기 명시한다.

## 접근
어떤 방식으로 갈지와, 검토했지만 안 택한 대안이 있으면 왜 안 택했는지 한 줄.

## 설계 참조
- 프로젝트 archi 경로/절 — 이번 태스크에 적용되는 책임과 계약.
- code-archi 문서 링크 — 구현할 파일·인터페이스·흐름의 정본.

## 작업 단계
1. …
2. …
저장소 절차가 코드 앞에 요구하는 산출물(설계 문서·합의된 테스트 케이스 등)이 있으면
그것도 하나의 단계로 여기 들어간다.
구현 방법을 정하는 데 필요한 설계는 pj-plan이 인계 전에 완성한다.
Simplifier를 선택했다면 구현 완료 → pj-simplify → pj-review 순서를 명시한다.

## 확인 방법
끝난 걸 어떻게 확인하는지. 실행할 테스트 명령어가 있으면 그대로 적는다.

## 결정 기록
the shared decision policy 로 확정한 것 중 **왜 그렇게 정했는지**. 무엇으로 정했는지는 위 섹션에 이미
반영돼 있어야 한다.

## 작업 인계

### 작업 유의사항
- 구현 중 놓치기 쉬운 제약: 구현 경계, 금지된 변경, 순서 제약, 사용자가 고른 스위치.

### 참조 문서
- `raw/tasks/{project}/design/{slug}/code-archi.md` — vault-relative, 코드 설계 정본.
- (repo 설계 문서를 쓰는 경우 위 항목 대신 repo 상대 경로를 적는다.)
- `추가 참조 경로 또는 안정된 URL` — 워커가 이걸 읽어야 하는 이유 한 줄.

### 리뷰어
- `<리뷰어 id>` — 이 작업에 이 리뷰어가 필요한 이유 한 줄 (해당 `when` 조건이 왜 맞는지).

### Simplifier
- 실행: run 또는 skip
- 이유: 단순화가 도움이 되는 구체적인 복잡성, 또는 필요 없는 이유.
- 범위: run일 때 정리할 태스크 변경 파일/영역. skip이면 생략.
```

## 규칙

**최초 요청은 불변.** 사용자가 실제로 요청한 것의 기록이다. 더 깔끔한 표현으로 고쳐 쓰는
순간 작업의 목적이 슬그머니 바뀐다. 요약이 필요하면 다른 섹션에서 한다.

**결정은 문서 전반에 반영하고, 기록에는 이유만.** the shared decision policy 로 범위를 좁혔으면 `목표` 가
바뀌어야 하고, 접근을 골랐으면 `접근` 과 `작업 단계` 가 바뀌어야 한다. `결정 기록` 에 한 줄
남기고 나머지를 그대로 두면 그 결정은 적용되지 않은 것이다 — pj-work 는 본문과 `작업 인계` 를
읽고 따르며, 결정 기록은 이유의 기록일 뿐 지시가 아니다.

**저장소 절차가 형식을 이긴다.** 저장소가 요구하는 산출물이나 순서가 있으면 그것을 따르고,
이 뼈대는 그 위에 얹는다. 뼈대에 맞추려고 저장소 절차를 접지 않는다.

**태스크 planner는 코드 설계와 구현 계획을 각각 작성한다.** code-archi와 plan은 별도 md다.
계획에 code-archi의 정확한 링크를 남긴다. 설계를 worker의 미래
작업으로 미루지 않는다. 사실로 확인한 코드와 새 제안을 구분하고, 작업 단계에는 위치·행동·
선행 조건·확인 방법을 담는다.

**프로젝트 archi 변경도 사용자와 결정한다.** 일반 실행은 the shared decision policy, pj-night는 자율 결정과
기록이다. 보드 승인 절차는 없다. 기존 archi 경로/절, 바뀐 계약, 이유는 code-archi에 적고
계획의 작업 단계·확인 방법·인계에도 적용한다. 정책 정본은
`../../pj/references/planning-decisions.md`다.

**섹션은 비우지 말고 지운다.** 해당 없는 섹션은 빈 채로 남기지 말고 통째로 뺀다. 빈 `## 접근`
은 "접근을 아직 안 정했다"와 "접근이랄 게 없다"를 구분해 주지 못한다.

**리뷰어는 옵셔널만 적는다.** `code` 리뷰어와(split 이면) 계획 리뷰는 항상 돌기 때문에 선택
대상이 아니고, 여기 적으면 "빼는 것도 가능하다"는 뜻이 돼서 transport 가 거부한다. 고른 것이
없으면 하위 제목을 지운다 — 빈 목록과 "옵셔널 리뷰어 없음"은 같은 뜻이다. 목록은
`raw/tasks/.../` 문서와 `worker.handoff` 이벤트 양쪽에 같은 id 로 들어간다: 문서는 사람이 읽고
이벤트는 transport 가 읽는다.

**Simplifier는 새 계획마다 명시한다.** `run`/`skip` 선택은 planner가 하고 명시적인 사용자
지시를 우선한다. 같은 선택을 작업 유의사항 한 줄로 넣어 기존 `cautions` 이벤트로도 전달한다.
새 이벤트 필드나 reviewer id를 만들지 않는다. `run`의 실행 위치는 구현 후, 리뷰 전이다.
실행 후 pj-simplify가 같은 하위 절에 결과(completed/no-change/skipped 또는 pending), 이유,
대상 파일과 확인한 코드 상태를 추가한다. 이전 계획에 선택이 없으면 자동 실행은 skip으로
취급하며, 그것만으로 예전 인계를 무효화하지 않는다.

**작업 인계는 항상 존재한다.** 워커는 별도 세션에서 cold 로 기동하며
이 섹션의 존재가 기동 게이트다 — 섹션이 없으면 "인계할 게 없다"와 "플래너가 아직 안 썼다"를
구분할 수 없다. 새 계획은 Simplifier 선택과 그 작업 유의사항을 항상 남기고, 그 외에 내용이
없는 하위 제목은 지운다. 유의사항은 `접근`·`확인 방법` 을 반복하지 않고(놓치기 쉬운
제약만), 참조 문서는 경로 + 이유 한 줄이지 본문 복사가 아니다. 기본 code-archi는 vault 기준
상대 경로와 `vault-relative`라는 이유 표시로 인계하며 worker가 vault 루트에서 읽는다. 본문의
클릭 가능한 링크는 절대 경로여도 되지만 이벤트에는 절대 경로나 `..`를 넣지 않는다. 빈 하위 제목은 지운다. 워커
기동이 실패하면 채팅 기록이 아니라 이 섹션에서 재시도한다.

**짧게.** 다음 사람이 이 문서만 보고 무슨 작업인지, 어디서부터 손대는지 알면 충분하다.
조사한 것을 전부 옮겨 적는 곳이 아니다.

## 로컬 경로는 써도 된다

jt 계열의 "로컬 경로 금지" 규칙은 여기 적용되지 않는다. 그 규칙의 근거는 티켓이 공유 Jira 에서
다른 사람 다른 머신으로 읽힌다는 것이었는데, 이 문서는 vault 안 개인 문서다. 워크트리 경로든
로컬 파일 경로든 도움이 되면 적는다.

다만 **저장소 코드를 가리킬 때는 저장소 상대 경로**를 쓴다 (`apps/main-web/src/…`). 워크트리가
정리되면 절대 경로는 죽지만 상대 경로는 살아 있고, 같은 코드를 다음 작업에서 다시 찾을 때 그게
유일하게 재사용 가능한 형태다.
