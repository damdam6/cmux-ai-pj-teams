# Portable setup contract

Resolve `SKILL_DIR` to the real directory of the executing `SKILL.md`, following symlinks.
`PJ_PACKAGE_ROOT` is its parent. The complete package is installed together, so
`$SKILL_DIR/../_shared/scripts/` always resolves. Invoke Python helpers with `python3`; direct
execution also works for helpers that have an executable bit. Bash helpers use `bash` or their
documented executable entrypoint.

At the start of a shell block that uses configured variables, load them:

```bash
# Set SKILL_DIR to the actual executing skill directory, then:
eval "$(python3 "$SKILL_DIR/../_shared/scripts/pj_config.py" --shell)"
```

The output is generated by the bundled helper with shell quoting. Never evaluate user text,
plan content, or external command output as shell code. Each new shell must load these exports;
Python helpers independently load the same configuration, including spawned subprocesses.

Priority: inherited `PJ_*` environment variable → package `config.local.json` → documented default.
`PJ_VAULT` is a plain data directory; Obsidian is not required. Task data is under its
`raw/tasks/` subdirectory. Keep it outside the distributed package. `PJ_REPOS_ROOT` is a directory
whose immediate children are main Git checkouts; the current worktree's checkout and siblings
are also discovered. `PJ_WORKTREE_ROOT` holds `{project-or-task}/{wtFolder}`.
`PJ_ALIASES` is the actual local JSON file, not the example.
The shipped `config.example.json` explicitly places it at
`~/.config/pj/repo-aliases.local.json` so registrations and commit policies survive package
replacement. If `PJ_ALIASES` is omitted, the legacy package-local default remains
`_shared/data/repo-aliases.local.json`. Keep an existing configured location when updating;
changing the path does not migrate the old file.

Read `$PJ_ALIASES` for repository settings. Never write paths or aliases into the example files.
The repository key is the main checkout directory name. Shared roots therefore require unique
checkout names. `wtFolder` values must be distinct for repositories in one project.
The alias example leaves `roleLaunchers` empty so it does not override the selected runtime.
Set only roles that need a repository-specific profile; explicit invocation hints take priority.

Repository registration also stores `commitPolicy` in this private alias entry. Follow
[commit-policy.md](commit-policy.md) to analyze a missing/stale policy and reuse it for
`pj-done` and `pj-wrap`. Existing ready policies do not require another history scan.

## CLI profiles

`_shared/data/launchers.local.json` maps profile IDs to `{runtime, argv, env?, reviewOption?, reviewers?}`. When absent the
example profiles run `claude`, `codex`, or optional `grok`, without model or permission flags.
The user can configure an installed CLI's model options in its argv array. An element is one
argument; shell aliases, command strings and shell substitutions are not interpreted.

Pass a profile ID verbatim as a launcher hint. To choose a model whose profile does not exist,
ask for/configure its actual supported CLI arguments; do not guess a model ID or effort flag.
Per-role precedence: explicit profile → repo `roleLaunchers` → runtime default.
Pass `--runtime codex` consistently when selecting Codex defaults; otherwise defaults are Claude.
The `--runtime` selector accepts only `claude|codex`; select Grok explicitly with
`--hint grok` or a configured role profile, not `--runtime grok`.
Reviewer-specific defaults are in `_shared/templates/pj/reviewers/*/reviewer.json`.
The selected profile's `runtime`, not its name, determines `/pj-*` versus `$pj-*` syntax.

The recorded review profile also selects the task's review option: its `reviewOption` value,
or otherwise its runtime (`claude`, `codex`, `grok`). `code` runs the exact recorded profile;
other spawned reviewers use their own defaults for that option. A profile may provide a
`reviewers` map of reviewer ID to profile ID, overriding the bundled per-reviewer defaults.
`launcher parse --role review --reviewer database --hint grok` resolves the database default
for the Grok option. A specific profile ID remains exact. Existing reviewer sessions retain
their original profile; this selection applies when they are first created.

To keep a separate account across spawned reviewers, use a named option profile whose
`reviewOption` is its own ID, and set that same option on its specialized profiles. For example,
add these entries to a copy of `launchers.example.json`, keeping the built-in profiles:

```json
{
  "codex-work": {
    "runtime": "codex", "argv": ["codex"],
    "env": {"CODEX_HOME": "~/.config/pj/codex-work"},
    "reviewOption": "codex-work",
    "reviewers": {"database": "codex-work-database"}
  },
  "codex-work-database": {
    "runtime": "codex", "argv": ["codex"],
    "env": {"CODEX_HOME": "~/.config/pj/codex-work"},
    "reviewOption": "codex-work"
  }
}
```

The account directory is user-selected and must already be configured/authenticated. `env`
is passed only to that child CLI; values are literal, with `~` expanded for `CODEX_HOME`.
Each specialized profile must name its own account environment as shown. Project skill links
remain `.codex/skills`; the selected account's hook configuration must independently support
the transport. No account directory, login, or hook is installed by profile selection.
Model/effort flags belong in each profile's explicit `argv`, using the installed CLI's options.

An explicitly requested additional `grok` reviewer remains a separate optional cross-check
with its own stream and default launcher. Choosing the Grok option alone changes the models
of the selected reviewers; it does not add this extra review lens.
The additional Grok role keeps its `grok` default even under a custom account option unless
that option explicitly maps `reviewers.grok` to another configured profile.

`pj-launch.py` executes the CLI and maintains its process registry while it is alive. Use it
for the initial board session as well as spawned sessions. No external registry plugin is needed.
The startup watcher inherits the board's exact profile and account environment; it has no
separate model key in `config.local.json`. Restart an old board through the current wrapper
to register its profile context, or use the watcher skill's explicit board-profile input.
No permission/trust bypass flags are supplied by this package.

## Language and local rules

Respond in the user's language. Task status headings (`할 일`, `진행 중`, `검토 대기`, `완료`)
and document schema headings are machine-readable keys: preserve them even when prose is in
another language. Repository instructions and the user's existing authorization govern actions.
Lint only changed files; skip a lint command that cannot be scoped. PJ does not require type
checking for completion, review or integration. Run a type check only when explicitly requested
or required by the repository. The bundled `pj-typecheck.py --changed-only` remains available
for that optional use; it is not called by the completion workflow.
